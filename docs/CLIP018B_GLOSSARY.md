# CLIP-018B — Glossary-Aware Query Understanding

> Историческое описание исходной реализации. После CLIP-018B-FIX расширенный текст
> изолирован в `retrieval_query`; актуальная архитектура, повторный A/B/C и решение о
> невключении описаны в [CLIP018B_FIX.md](CLIP018B_FIX.md).

## Назначение и граница

CLIP-018B добавляет детерминированное раскрытие утверждённых корпоративных сокращений
после формирования актуального `resolved_query` и до `route_and_plan` AI-Агента. Модуль
не вызывает LLM, не создаёт evidence, не цитируется как источник и не меняет Baseline
RAG. При `GLOSSARY_ENABLED=false` поисковая формулировка и прежнее поведение сохранены.

Один расширенный текст, содержащий расшифровку и исходное сокращение, передаётся в
существующий retrieval. Поэтому глоссарий не добавляет поисковый вызов, не создаёт второй
fusion pipeline и сохраняет резерв `AGENT_MAX_SEARCH_CALLS` для targeted retry. При
совместном включении Multi-Query расширенный текст становится исходным вариантом, а
прежние межзапросный RRF, дедупликация и общий бюджет остаются обязательными.

## Приватный файл и формат

Полный словарь заказчика хранится только локально:

```text
storage/glossary/customer_v1.json
```

Каталог `storage/` исключён из Git. Фактический локальный файл содержит 50 отдельных
записей: групповые строки `КСУП, ИСУП` и `КС-2, КС-3` разделены для однозначного
сопоставления. Версия — `customer_v1`, источник — `customer_provided`, SHA-256 —
`44049beecd1306d21652b100fd2ebb10d710fb4d7071dde33f2db01892c3649e`.

Синтетический пример формата:

```json
{
  "version": "synthetic-v1",
  "source": "synthetic_test",
  "content_sha256": "<sha256 канонического JSON без этого поля>",
  "terms": [
    {
      "abbreviation": "АБВ",
      "expansion": "Синтетический корпоративный термин",
      "synonyms": [],
      "ambiguous": false,
      "context_terms": [],
      "case_sensitive": false
    }
  ]
}
```

Загрузчик ограничивает размер файла, требует UTF-8 JSON, запрещает неизвестные поля,
валидирует каждую запись и сверяет checksum канонического содержимого. Пустой,
повреждённый, частично валидный файл, неверная checksum или повторный alias останавливают
запуск при включённом feature flag. Частичная загрузка запрещена.

## Сопоставление и неоднозначность

- Границы учитывают кириллицу, латиницу, цифры и дефис; подстроки слов не заменяются.
- Регистр не важен, кроме явно помеченных `case_sensitive` терминов. Это предотвращает
  раскрытие русского предлога `по` как `ПО`.
- Первое безопасное вхождение заменяется на `Расшифровка (СОКРАЩЕНИЕ)`: расшифровка
  помогает dense/BM25, а исходная форма остаётся доступной для документов.
- Повторное вхождение того же сокращения и уже присутствующая расшифровка не раскрываются
  ещё раз.
- `ambiguous=true` требует хотя бы один утверждённый для записи `context_terms`. Без него
  текст не меняется, а trace получает `ambiguous_without_context`.
- В customer v1 консервативные ограничения заданы для коротких потенциально неоднозначных
  терминов, включая `АП`, `ДС`, `ЗП`, `КП`, `ПА` и `ПО`. Это техническая политика
  безопасного использования, а не новый корпоративный факт.
- Если пропущенная неоднозначность действительно мешает выбрать применимый документ,
  существующий evidence assessment запрашивает уточнение. Глоссарий сам не придумывает
  подразделение, этап, дату или роль.

Например, `Кто согласует ДС после ЗНИ?` преобразуется в поисковое представление с
`Дополнительное соглашение (ДС)` и `Запрос на изменение (ЗНИ)`. Вопрос
`Кто отвечает по договору?` остаётся неизменным.

## Диалог, evidence и traces

В уточняющем диалоге сначала формируется bounded `resolved_query` из исходного вопроса и
явных ответов пользователя. Только затем к этому тексту применяется глоссарий. Новый
самостоятельный вопрос после `completed` проходит тот же путь; определения и source IDs
предыдущего хода не переносятся.

`SearchTrace.question` сохраняет пользовательский текст. `details` дополнительно содержит:

- `resolved_query` и `glossary_search_query`;
- `glossary_enabled`, `glossary_used`, `glossary_query_changed`;
- версию и SHA-256;
- числа найденных, применённых и пропущенных раскрытий;
- агрегированные причины пропуска;
- latency и `glossary_additional_retrieval_calls` (сейчас всегда `0`).

Полный словарь и его определения не логируются. После retrieval сохраняются PostgreSQL
visibility gate, assessment, conflict/scope/temporal guards, citation и grounding
validation. Источниками остаются только реальные активные документы.

## Конфигурация

Безопасные defaults в `.env.example`:

```dotenv
GLOSSARY_ENABLED=false
GLOSSARY_PATH=storage/glossary/customer_v1.json
```

Действующий `.env` в CLIP-018B не изменялся. Публичного endpoint для чтения словаря нет;
`/api/v1/capabilities` раскрывает только факт включения.

контрольных/негативных сценариев. Использованы те же четыре документа и изолированные
ресурсы `clip017_customer_v1_offline`, Multi-Query OFF и одинаковые параметры. Corpus
переиспользован без переиндексации.

В B обработано 43 вхождения: 38 раскрытий применены, 5 консервативно пропущены;
false expansion на размеченных негативных кейсах — `0.0`. Дополнительных retrieval calls
— `0`; среднее время модуля — `0.0326 ms`, суммарно `0.881 ms`.

Retrieval-эффект смешанный: ранняя позиция и Passage Recall@5 выросли, но Document
Recall@3 снизился. Главное — улучшение retrieval не превратилось в устойчивое улучшение
ответов: grounded answers, abstention и clarification ухудшились, а два дополнительных
LLM-вызова появились из-за изменившихся outcomes, не из-за отдельного вызова глоссария.
Gold остаётся `draft`, автоматические fact/citation proxies не заменяют экспертный review.

**Решение:** не включать `GLOSSARY_ENABLED` на публичном стенде по результатам v1. Сначала
нужен case-level ручной review ухудшений и отдельный измеримый эксперимент с более
консервативным поисковым представлением/политикой терминов без изменения gold.

Неизменный 36-кейсный CLIP-017 набор также повторён с Glossary OFF:
`clip017_customer_v1-20261127T144245+0300-151694b5-59bc42af`. Dataset и corpus hashes
совпали с B2. Document Recall@3 `0.9056`, Passage Recall@5 `0.6611`, MRR `0.8472`,
grounded answer rate `0.5000`, correct abstention `0.3333`, clarification success
`0.1667`, technical error rate `0.0556`, а также `38` search и `97` LLM calls — точно
совпали с B2. Это подтверждает отсутствие регрессии в выключенном режиме на этом
контрольном прогоне; gold по-прежнему `draft`.

## Будущее ручное включение и rollback

Только после отдельного разрешения владельца:

1. Проверить Git SHA/status, процессы, read-only health/ready и verified backup; сохранить
   текущие `.env` и frontend bundle вне Git.
2. Проверить приватный файл и checksum командой загрузчика, затем выполнить полный suite и
   сопоставимый A/B. Не включать функцию при ухудшении answer-quality метрик.
3. В согласованное окно вручную добавить `GLOSSARY_PATH` и установить
   `GLOSSARY_ENABLED=true`; перезапустить только FastAPI штатным способом владельца.
4. Проверить capabilities, readiness и разрешённый синтетический диалог. Caddy, Funnel,
   Ollama, документы и поисковые индексы не менять.

Rollback: вернуть `GLOSSARY_ENABLED=false` (или прежний `.env`/SHA) и перезапустить только
FastAPI. Миграций, переиндексации и очистки хранилищ не требуется; старые trace JSON-поля
безопасно игнорируются.

## Ограничения

- Контекстная неоднозначность определяется лексически и допускает false positive/negative.
- Глоссарий не исправляет опечатки, морфологию или неизвестный жаргон.
- Нет административного CRUD, hot reload и публичной выгрузки словаря.
- Положительный эффект на итоговые ответы не доказан; включение по умолчанию запрещено.
- Нет production identity/ACL, OCR и гарантированного разбора сложных таблиц.
