## 1. Назначение
Этот документ отделяет **уже измеренные результаты** от **планируемой оценки на реальных регламентах**. Retrieval-метрики, корректность ответа, цитирование, обоснованность отказов, стоимость и задержка оцениваются отдельно. Числа из разных наборов данных нельзя трактовать как единый A/B-тест.

## 3. Определения метрик
Для вопроса с непустым вручную проверенным множеством релевантных источников `Gold(q)` и ранжированной выдачей `TopK(q)`:

- **Recall@K** = `|Gold(q) ∩ TopK(q)| / |Gold(q)|`. Полнота обнаружения нужных источников.
- **Precision@K** = `|Gold(q) ∩ TopK(q)| / K`. Доля релевантных позиций в первых K результатах. Указать правило при выдаче короче K.
- **MRR** — среднее обратное место первого релевантного источника.
- **nDCG@K** — качество порядка с учётом экспертных уровней релевантности, если они размечены.
- **Evidence / citation support** — отдельно проверяем, что утверждения ответа действительно подтверждаются процитированными фрагментами.
- **Correct abstention** — корректный отказ при отсутствии данных либо невозможности устранить противоречие.

Метрики рассчитывать **как минимум на двух уровнях**: документ (document_id) и фрагмент / положение (стабильный `gold_passage_id`). Для четырёх документов `Recall@5` и `Recall@8` на уровне документа малоинформативны; приоритетны Document Recall@1/@3, Precision@1/@3, Passage Recall@5/@8 и качество ответов.

Случаи с отсутствующими релевантными источниками не включать в средний Recall/Precision путём искусственного присвоения нуля или единицы: оценивать их отдельно как `should_abstain`.

## 4. План оценки на регламентах заказчика

**Набор:** ориентир 30–40 экспертно размеченных вопросов из четырёх действующих документов. Типы сценариев:
- прямой вопрос по одному документу;
- вопрос по нескольким документам;
- неоднозначность и требуемое уточнение;
- отсутствие ответа в корпусе;
- реальное противоречие (только если подтверждено документами);
- отдельный сценарий утверждённого знания службы качества после его публикации.

Для каждого сценария зафиксировать `case_id`, исходный вопрос, expected outcome, документы, точные опорные цитаты, ограничения области применения, релевантные passage IDs, допустимые ответы, запрещённые выводы и имя/дату проверившего эксперта. Разметка должна основываться на документах, а не на ответах оцениваемой LLM.

**Режимы одного честного A/B-набора:** Baseline RAG; Strict Agent / Multi-Query OFF; Strict Agent / Multi-Query ON. Ollama и OpenAI сравнивать отдельными парами при одинаковых corpus/index/gold и явно зафиксированном provider/model. При необходимости оценить reranker как независимый фактор, не смешивая его с Multi-Query.

Фиксировать Git SHA, dataset hash, corpus hash, список активных версий источников, модель embeddings, LLM/provider, reranker, настройки генерации, top-K, лимиты агента, дату, hardware, latency, tokens, ошибки. Выполнить один exploratory run и затем повторяемые контрольные прогоны; для оценки вариативности LLM желательно не менее трёх повторов.

**Безопасность:** использовать отдельные PostgreSQL schema, Qdrant collection, OpenSearch index и storage. Не менять действующий публичный стенд, `.env`, SMTP и production индексы. Реальные вопросы, цитаты, тексты и индивидуальные case-level outputs не коммитить в публичный GitHub без отдельного разрешения. В репозитории размещать только разрешённую обезличенную сводку и методику.

## 6. Требования к итоговому протоколу
1. Разделить retrieval quality, answer factuality, citation support, abstention, latency и cost.
2. Для каждого показателя указать уровень гранулярности, K, число оценённых вопросов, macro/micro-агрегацию и политику исключения `not applicable`.
3. Фиксировать **все** ошибки и пропуски; не исключать неудачные случаи из итогов незаметно.
4. Сравнивать только прогоны с одинаковыми corpus/dataset hashes и неизменным набором gold.
5. Хранить машиночитаемые `run.json`, `cases.jsonl`, `report.md` и сравнительный `comparison.md`; конфиденциальные case-level файлы оставлять локально.
6. Провести ручной review всех конфликтов, отказов и спорных ответов; зафиксировать reviewer/date/decision.
7. В выводе не называть валидный номер `[N]` доказательством семантической корректности.
8. Внести подписанный/утверждённый сводный отчёт в документацию проекта после эксперимента.
