# CLIP-017-EVAL — оценка на регламентах заказчика

**Дата прогона:** 26 ноября 2026 года

**Статус:** exploratory evaluation завершена; gold set остаётся `draft` до внешнего экспертного review

**Код прогона:** commit `cc9204456f37b5824d8e984495e974d198936ea5`, source tree SHA-256 `417014f41e2baa25a9ebf45f86025836f229fbc2e3a98bc17932caf15e121cc5`

**Итог:** baseline работоспособен, агентный режим блокируется ошибкой разбора структурированного ответа; преимущества Multi-Query для ответа пользователю не доказаны.

## 1. Объём и статус разметки

Оценка выполнена на четырёх DOCX-регламентах, полученных из предоставленной папки Google Drive. Оригиналы и case-level результаты хранятся только локально в исключённых из Git каталогах `eval/runtime/` и `eval/results/`. Все документы успешно извлечены и проиндексированы в отдельные ресурсы CLIP-017; основные ресурсы проекта не затрагивались.

| Категория | Кейсов |
|---|---:|
| Прямой факт из одного документа | 14 |
| Несколько документов | 7 |
| Неоднозначность / уточнение | 6 |
| Недостаточно данных | 6 |
| Область применения и ограничения | 3 |
| Подтверждённое реальное противоречие | 0 |
| **Всего** | **36** |

Подтверждённого противоречия между регламентами не найдено: различия относятся к разным дирекциям, стадиям и условиям. Создавать искусственный conflict-case было бы неверно. Все 36 кейсов имеют `gold_status=draft`, `reviewer=null`, `reviewed_at=null` и `manual_review_required=true`. Файлы `clip017_customer_v1_review.md` и `.csv` подготовлены для независимого экспертного review. Поэтому результаты являются воспроизводимым exploratory baseline, а не утверждённой оценкой качества заказчиком.

## 3. Условия эксперимента

Все режимы использовали `qwen3.5:9b` через локальный Ollama, `temperature=0`, `think=false`, `num_predict=512`, embeddings `BAAI/bge-m3` на CPU, dense + BM25 + RRF, reranker OFF. Внешние LLM/API не использовались; денежная стоимость не измерялась. Каждый прогон завершил 36/36 вызовов evaluator без необработанных runtime-исключений.

| Обозначение | Режим | Experiment ID |
|---|---|---|
| A | Baseline RAG | `clip017_customer_v1-20261126T183015+0300-cc920445-417014f4` |
| B | Strict Agent, Multi-Query OFF | `clip017_customer_v1-20261126T183408+0300-cc920445-417014f4` |
| C | Strict Agent, Multi-Query ON | `clip017_customer_v1-20261126T183626+0300-cc920445-417014f4` |

Commit SHA в артефактах предшествует итоговому коммиту задачи, а `dirty=true`: по правилу «одна задача — один коммит» эксперименты выполнялись до формирования отчёта. Точная версия незакоммиченного дерева зафиксирована одинаковым source tree SHA-256 во всех трёх `run.json`.

## 4. Retrieval

Метрики — macro mean только по 30 кейсам с непустым gold. Шесть insufficient-data кейсов имеют retrieval-метрики `not applicable`, а не искусственные 0/1. Document ranking предварительно дедуплицируется по `source_id` с сохранением первого ранга. Passage ID устойчив к UUID чанка и строится по source + нормализованному parent context. Precision использует фиксированный знаменатель K.

Автоматические fact/citation проверки являются узкими regex/лексическими proxy и не доказывают entailment. Все ответы требуют ручного review.

Baseline правильно классифицировал outcome в 27/36 кейсах. При этом все шесть insufficient-data ответов содержательно сообщали об отсутствии нужных сведений, но API вернул `answered`, а не ожидаемый защищённый outcome `quality_review_required`; поэтому Correct abstention = 0. Это различает «текст похож на отказ» и корректное системное состояние.

В шести multi-turn сценариях ни один режим не прошёл детерминированный критерий успешного уточнения. Это не доказывает, что текст диалога всегда бесполезен, но показывает отсутствие измеренного end-to-end успеха по текущему draft gold.

## 6. Анализ отдельных кейсов

- `REAL-001` (назначение РП в Дирекции ИБ) — baseline дал требуемый факт с валидными ссылками и прошёл automatic grounding checks. Оба agent-прогона вернули `technical_error` на `assess_evidence` при наличии найденных источников.
- `REAL-004` (первая строка таблицы карточки проекта) — после исправления DOCX extraction baseline обнаружил и процитировал табличное положение. До исправления эти данные вообще не попадали бы в индекс.
- `REAL-026` — Multi-Query добавил ожидаемое положение: Document Recall@3 изменился 0 → 1, Passage Recall@5/@8 — 0 → 1. Итоговый ответ всё равно не прошёл grounding из-за технического отказа агента.
- `REAL-009` — расширение ухудшило passage retrieval: Recall@1/@5 изменился 1 → 0. В `REAL-011` и `REAL-036` Document Recall@1 изменился 1 → 0, а MRR — 1 → 0,5. Это примеры цены дополнительного поискового расширения.
- `REAL-002` — passage Precision@3 снизился с 1,0 до 0,6667; для большинства остальных кейсов Multi-Query не изменил релевантные gold-положения.
- `REAL-033` — единственный correct abstention в C: агент не стал выводить автоматическую отмену остальных документов «как более новых» и вернул `quality_review_required`. B завершился технической ошибкой; baseline сформулировал содержательный отказ, но вернул неверный outcome `answered`.
- `REAL-022` — пример требуемого уточнения, который не состоялся: агент завершился `technical_error` до полноценного второго хода; baseline также не выдал `clarification_required`. Clarification success остаётся 0/6.
- Реального противоречия не найдено, поэтому положительный пример conflict handling отсутствует и метрика остаётся N/A.

Третий сценарий заказчика («нет ответа — служба качества») проверялся без SMTP и без production-обращений. Шесть insufficient-data кейсов воспроизводят отсутствие ответа, но end-to-end публикация утверждённого экспертного знания в рамках этой серии не создавалась.

## 8. Обнаруженные дефекты и ограничения

1. **Блокирующий дефект Agent.** B: 34/36, C: 33/36 outcomes — `technical_error` с `reason_code=evidence_assessment_failed`. Узел `assess_evidence` не разобрал структурированный JSON от модели: 64 раза отсутствовал JSON object, ещё три ответа C содержали синтаксически повреждённый JSON. Ошибка воспроизводима и объясняет почти нулевые answer/citation метрики агента.
2. **DOCX extraction до исправления пропускал таблицы.** В документе Дирекции ИБ терялась реальная таблица из восьми строк (725 символов ячеек). Extraction теперь сохраняет абзацы и таблицы в порядке документа; merged cells не дублируются. Кейс `REAL-004` подтверждает доступность таблицы для baseline.
3. **Document-level evaluator завышал влияние повторных чанков.** Ranking теперь дедуплицируется по документу до расчёта Recall/Precision/MRR/nDCG.
4. **Gold не утверждён.** Разметка подготовлена по точным цитатам исходников, но не подписана независимым экспертом. Нельзя использовать числа как финальную приёмку заказчика.
5. **Нет подтверждённых conflict-cases.** Conflict handling остаётся `not measured`, а не 0.
6. **Один прогон на режим.** Вариативность локальной LLM и доверительные интервалы не оценены.
7. **Citation support автоматический.** Лексическое совпадение и валидный `[N]` не заменяют ручную проверку доказательности.
8. **Частичный старый изолированный ресурс** после заблокированного сетевого обращения оставлен нетронутым и требует отдельного разрешения на очистку.

## 10. Решение

- Для демонстрации на текущем состоянии использовать только baseline с явным предупреждением о draft gold и известных ошибках abstention/clarification.
- Не включать Strict Agent в демонстрационный default до исправления/валидации structured-output на `assess_evidence` и повторения тех же A/B/C прогонов без изменения gold.
- Не объявлять Multi-Query улучшением: выигрыш Recall@3/Passage Recall@8 сопровождается ухудшением раннего ранжирования, ростом latency и отсутствием улучшения итоговых outcomes.
- Следующий измеримый шаг: эксперт утверждает review-файлы; затем исправляется JSON-contract агента, фиксируется новая версия кода и повторяются минимум три контрольных прогона на неизменных dataset/corpus hashes.

Исторические результаты CLIP-003/005/006/016 остаются синтетическими и не смешиваются с этой таблицей.
